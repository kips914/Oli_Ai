# Архитектура OLI 1.12.6

Документ для тех, кто будет дорабатывать код: что где лежит, как проходит
запрос, какие есть ограничения безопасности.

## Поток одного сообщения

```
Пользователь (WPF / Telegram / Android-приложение)
        │
        ▼
AgentSession.SendAsync(text)
        │  собирает system prompt (Persona + ToolPromptSection)
        │  добавляет память и профиль
        ▼
   ┌───────────────────────────────┐
   │  цикл (не более 8 шагов)      │
   │  1. есть OLI_TOOL: … ? ───────┼──► ToolDispatcher ──► WorkspaceEngine
   │  2. есть OLI_SEARCH: … ? ─────┼──► WebSearch (DDG/Bing/Mojeek/Wikipedia)
   │  3. есть OLI_OPEN: … ? ───────┼──► WebSearch.ReadPageAsync
   │  иначе — это ответ           │
   └───────────────────────────────┘
        │
        ▼
   финальный текст + OLI_REMEMBER + send_file
```

Каждый шаг цикла — отдельная генерация. Промежуточные ответы модели попадают в
историю, чтобы она видела, что уже сделала. Ответ стримится в UI
(`AgentEventKind.Delta`), в Telegram — редактированием сообщения «⏳ Думаю...».


## Подключение и чаты (1.12.3)

Подключение и чаты раньше были реализованы в четырёх местах по-разному. Теперь
есть ровно два ядра, и все остальные места — тонкие обёртки.

```
        ┌───────────────────────────────────────────────┐
        │ OLI.Core/ConnectionCore.cs                    │
        │ адрес · IsLoopback · CandidateOrder           │
        │ код подключения (склейка/разбор)              │
        │ Classify + Describe (одно правило здоровья)   │
        │ Beacon (UDP 52345) · RetryPolicy              │
        └───────┬───────────────┬───────────────┬───────┘
                │               │               │
     OLI.Engine/OliServerClient  LanBeacon   Android: OliApi.parseJoinCode,
     (проба, вход, чат, чаты)     (рассылка)  BeaconScanner, chat-очередь
```

Правило здоровья одно на всех:

| Условие | Состояние | Что говорит пользователю |
|---|---|---|
| нет ответа | `ServerDown` | «Пульт админа» → «🛡 Открыть порт», либо код подключения |
| ответил не `oli-server` | `NotOli` | проверьте порт (по умолчанию 8765) |
| `llama == true` | `Ready` | движок работает |
| `llama == false` | `EngineDown` | запустите Ollama / llama.cpp |

Чаты:

```
        ┌───────────────────────────────────────────────┐
        │ OLI.Core/ChatCore.cs (чистые правила)         │
        │ ChatEntry · Clean · MakeTitle · Trim          │
        │ ToModelHistory · VisibleText · IsPersistable  │
        └───────────────┬───────────────────────────────┘
                        │
        OLI.Server/Chats/ChatStore (блокировка на аккаунт,
        кэш в памяти, атомарная запись .tmp → переименование)
                        │
        HTTP: /api/chat, /api/chats, /api/chats/{id},
              /api/chats/{id}/rename, /api/chats/latest
```

Ключевые решения (каждое закреплено тестом в `OLI.SelfTest`):

- **Заголовок чата** — первое сообщение пользователя, одна строка, ≤ 60 символов.
- **История для модели** — последние 24 сообщения, без ошибок, пустых и системных.
- **Удалённый чат не оживает**: `ChatStore.Append` возвращает `null`, сервер отвечает
  `409 {deleted:true}`, приложение показывает причину.
- **Пустой ответ модели** показывается фразой «⚠ Пустой ответ модели», а не пустым пузырём.
- **Телефон не шлёт два сообщения одновременно**: `Mutex` + «эпоха» чата, поэтому
  поздний ответ не попадает в другой чат.
- **`503` не повторяется** (`RetryPolicy.ShouldRetry`), потому что выключенный движок
  сам не включится за 700 мс.
- **Поиск сервера**: UDP-маяк с реальным портом, затем скан подсети как запасной путь.

Проверить всё это вживую можно кнопкой «📱 Проверить путь телефона» в пульте админа:
она проходит те же шаги, что приложение на телефоне.

## Старт приложения (1.12.6)

`OnStartup` — самое опасное место в WPF-приложении: всё, что там ждёт, происходит до
первого окна. Порядок намеренно простой и без единого блокирующего ожидания:

```
mutex единственного экземпляра ── занят → сообщение + Shutdown(0)
      │
      ▼
IsOliServing(port)      Task.Run(OliAnswersAsync, 700 мс/запрос) + Wait(3 с)
      │                  любое сомнение → false (открыть мастер — безопасно)
      ├─ живёт OLI → мастер пропускается
      └─ иначе и настройка не завершена → SetupWindow.ShowDialog()
      ▼
new MainWindow() → Show() → _startedOk = true
```

Правило, из-за нарушения которого 1.12.5 не открывалась: **асинхронный вызов нельзя
ждать на UI-потоке**. `await` внутри метода возвращается на `SynchronizationContext`
интерфейса, а `.GetAwaiter().GetResult()` держит этот же поток — взаимная блокировка
навсегда. Поэтому проба вынесена в `Task.Run` и ограничена по времени.

Три независимых предохранителя:

| Предохранитель | Что ловит |
|---|---|
| Сторож 10 с (`ArmStartupWatchdog`) | окно не создалось или невидимо → сообщение + путь к логу |
| `EnsureOnScreen` в `Loaded` | окно сохранено за пределами рабочего стола (отключён монитор) |
| `OnDispatcherUnhandledException` | ошибка в обработчике → предупреждение, приложение живёт |

Мастер настройки защищён `_finishing` от повторного входа в `Done_Click` (двойной
клик раньше приводил к падению на `DialogResult`), а `OnClosed` освобождает порт в
фоне через `Task.Run(App.EndSetup)`, чтобы закрытие окна не ждало сокет.

Лог пишет этапы старта (`APP Старт OLI …` → `APP Окно OLI открыто`), поэтому вопрос
«почему не открылось» решается чтением трёх строк, а не догадками.

## Порт сервера (1.12.5)

```
OLI.exe стартует
     │
     ├─ mutex Local\OLI.Client.SingleInstance ── занят? → «OLI уже запущен», выход
     │
     ├─ OLI уже отвечает на порту? ── да → мастер не нужен, окно открывается сразу
     │
     └─ MainWindow.StartServerAsync (одна попытка, _serverStarting)
              │
              ▼
        ServerHost.ResolvePortAsync
              │
              ├─ никто не слушает и порт свободен ─────────────→ занимаем как есть
              ├─ отвечает OLI (/ или /api/health) ─────────────→ переиспользуем (_reuseExisting,
              │                                                   StopAsync ничего не гасит)
              └─ занят чужой программой → PortGuard.FindFree → переезд + PortNotice
```

Три правила, из которых всё следует:

1. **Одна копия OLI.** Порт — общий ресурс машины; два экземпляра гарантированно
   конфликтуют. Второй запуск не борется за порт, а показывает окно первого.
2. **Проверяем тот адрес, который займём.** `PortGuard.IsFree(port, host)` биндит
   именно `Options.Host` (частая ошибка — проверять `0.0.0.0`, а слушать
   `127.0.0.1`: проверка «свободно», а Kestrel падает).
3. **Вопрос «кто там» задаётся дважды.** `IsListening` — есть ли кто-то вообще;
   `OliAnswersAsync` — это OLI или чужой. Второй смотрит и `/` (быстрый баннер),
   и `/api/health` (он опрашивает движок и может быть медленным, пока грузится
   модель), поэтому живой OLI не принимается за постороннего.

Мастер первого запуска держит временный `ServerHost`. Он освобождает порт в
`OnClosed` (а не только по кнопке «Готово»), переиспользует уже созданный
`_setupServer` и передаёт туннель главному окну через `App.TakeSetupTunnel()`,
чтобы `cloudflared` не запускался дважды.

`MainWindow.StartServerAsync` защищён `_serverStarting` и `DescribeStartFailure`:
любая неудача порта превращается в строку вида «порт 6767 занят: steam.exe
(PID 4210). Закройте лишний OLI или смените порт», а стектрейс уходит в лог.

## Первый запуск и туннель (1.12.4)

```
OLI.exe (первый запуск)
     │
     ├─ ComponentInstaller  → cloudflared.exe (размер + MZ + SHA-256, зеркало)
     ├─ ServerHost.StartAsync            → порт 6767 + UDP-маяк
     ├─ FirewallHelper.EnsurePortOpen    → правило для порта (UAC)
     ├─ TunnelManager.StartAsync         → публичный https-адрес
     │        ├─ Launch (IPv4 + http2)
     │        ├─ нет адреса → повтор с флагами cloudflared по умолчанию
     │        └─ watchdog (20 с) → перезапуск до 3 раз
     └─ SetupCheckCore.RunAsync          → мини-тест: сервер · Wi-Fi · интернет
```

Проверка подключения — это **три вопроса**, и каждый отвечает за свой симптом:

| Шаг | Что проверяет | О чём говорит провал |
|---|---|---|
| Сервер OLI | `127.0.0.1:порт/api/health` | сервер не запущен или порт занят |
| Адрес в Wi-Fi | `192.168.x.x:порт` | **брандмауэр** (loopback работает, снаружи — нет) |
| Доступ из интернета | публичный адрес туннеля | cloudflared не скачался / провайдер блокирует |

Повторный запуск — «Пульт админа» → «🧰 Установка и проверка»; установленное заново
не скачивается, поэтому это безопасно нажимать когда угодно.

## Протокол инструментов

Модель не использует function calling — он ненадёжен на маленьких GGUF.
Вместо этого — строковый протокол, который одинаково работает в UI и Telegram:

```
OLI_TOOL: save_file {"path":"docs/a.md","content":"..."}
OLI_SEARCH: погода в Санкт-Петербурге
OLI_OPEN: https://example.com/page
OLI_REMEMBER: пользователь учится на программиста
```

* `OLI_TOOL` — можно несколько строк подряд; JSON допускается многострочный
  (парсер считает баланс скобок с учётом строк).
* `OLI_SEARCH` / `OLI_OPEN` срабатывают только если это **весь** ответ —
  случайное упоминание в тексте не запускает поиск.
* `OLI_REMEMBER` вырезается из ответа и сохраняется в память.

Добавить инструмент: метод в `ToolDispatcher.ExecuteOneAsync`, строка в
`ToolPromptSection.Build` (и в `ToolDispatcher.DescribeCall` для UI).

## Безопасность

**Workspace.** Всё, что делает модель, проходит через `PathGuard.Resolve`:
абсолютные пути, `..`, диски, UNC, `~`, управляющие символы и URL отклоняются;
результат проверяется на вложенность в корень. Распаковка zip проверяет каждый
entry (zip-slip), запись и распаковка заряжаются в квоту. Команды — только из
белого списка, запускаются в корне песочницы, с таймаутом и обрезкой вывода.
Для Telegram есть отдельный флаг «разрешить команды» (по умолчанию выключен).

**Сеть.** `WebSearch` блокирует localhost, приватные диапазоны, link-local и
`.local`/`.internal` (SSRF), соблюдает чёрный список и (в режиме списка) —
белый. Страницы читаются с лимитом 8 МБ и 12 000 символов текста.

**Telegram.** Токен не хранится в туннелях — подставляется в URL в момент
запроса. Опциональный `RELAY_SECRET` защищает воркер. Список разрешённых
Telegram ID ограничивает доступ.

## Тема и UI

`OLI.Client/App.xaml` — дизайн-система (цвета, стили кнопок, полей, табов,
карточек). `App.ApplyTheme` перезаписывает кисти для светлой/тёмной/системной
темы. Все элементы интерфейса ищут кисти по ключу, поэтому новые экраны
автоматически поддерживают темы.

## Модели

`OLI.Core/ModelCatalog.cs` (UI) и `scripts/models.json` (движок) должны
содержать одинаковые `gguf`-спеки. `start-llama.ps1` берёт модель из
`settings.json → ModelGguf`, поэтому смена модели в UI + `-Restart` перезапускает
сервер с новым `-hf`.

## CI

`.github/workflows/build-exe.yml` на каждый push собирает библиотеки, гоняет
`OLI.SelfTest`, публикует single-file `OLI.exe` и на теге `v*` прикладывает
`OLI.exe` + `OLI-win-x64.zip` к GitHub Release.

## Многопользовательский режим (1.9)

```
Android ──HTTP──► OLI.Server (Kestrel, 0.0.0.0:8765)
Telegram ───────►      │
WPF «Пульт админа» ────┤ (loopback)
                       ▼
                AccountStore  ── accounts.json (только хеши паролей и токенов)
                UserWorkspaceRegistry ── users/<accountId>/ (по 1 ГБ)
                AgentSession на пользователя ── llama.cpp (общая модель, общий WebSearch)
```

* **Пароли**: `PBKDF2-HMAC-SHA256`, 210 000 итераций, 16-байтовая соль на
  пользователя, 32-байтовый хеш; сравнение `FixedTimeEquals`. Открытого пароля
  нет нигде — админ может только задать новый (сброс) и разослать его.
* **Токены**: 32 случайных байта, на сервере хранится SHA-256; 30 дней; не более
  8 устройств на аккаунт; смена/сброс пароля и блокировка отзывают все токены.
* **Файлы**: у каждого аккаунта своя `WorkspaceEngine` с `PathGuard` внутри
  `users/<id>/`; квота — `ServerSettings.UserQuotaBytes` (по умолчанию 1 ГБ);
  `run_command` для пользователей сервера выключен на уровне `AgentSession`.
* **Админ-API**: `/api/admin/*` разрешён с loopback (сам ПК) или по заголовку
  `X-OLI-Admin: <AdminToken>`, либо аккаунту с `IsAdmin`.
* **Телефон**: логин/пароль — `EncryptedSharedPreferences` (AES-256-GCM, ключ в
  Android Keystore), исключены из резервных копий; адрес сервера можно зашить
  при сборке: `-POLI_DEFAULT_SERVER=http://192.168.1.10:8765`.
